## 1. 프로젝트 개요

Karpathy의 LLM Wiki 개념에 **CPU 캐시 계층 구조**를 도입하여, LLM의 컨텍스트 윈도우를 효율적으로 사용하는 것에 집중한 구현체. Claude Code를 LLM 엔진으로, Logseq 또는 Obsidian을 위키 인터페이스로 사용한다.

**핵심 컨셉**: "모든 지식을 매번 로드할 필요 없다. CPU가 L1/L2 캐시를 쓰듯, LLM도 지식을 계층화해야 한다."

## 2. 구현 방향성

| 구분 | Karpathy 원본 | llm-wiki (MehmetGoekce) |
|------|--------------|------------------------|
| 메모리 모델 | 단일 레이어 (위키 전체) | **L1/L2 캐시 계층** |
| 위키 앱 | Obsidian만 언급 | **Logseq + Obsidian 이중 지원** |
| 셋업 | 수동 | **setup.sh 자동화** |
| 보안 | 언급 없음 | **크레덴셜 L1 격리** |
| 스키마 | 추상적 가이드 | **8개 네임스페이스 + 5개 페이지 타입** |

## 3. L1/L2 캐시 아키텍처

CPU 캐시 계층에서 영감을 받은 2단계 지식 관리:

```
┌─────────────────────────────────────────┐
│              L1 (Claude Memory)          │
│                                          │
│  매 세션마다 자동 로드 (~10-20 파일)       │
│  ┌────────────────────────────────────┐  │
│  │ - 운영 규칙/제약사항                │  │
│  │ - 개인 식별 정보 (선호, 스타일)      │  │
│  │ - 크레덴셜/API 키                  │  │
│  │ - 위험한 실수를 방지하는 핵심 정보    │  │
│  └────────────────────────────────────┘  │
│  ⚡ 즉시 접근, 항상 메모리에 상주          │
└─────────────────────────────────────────┘
                    │
                    ▼ 필요할 때만 로드
┌─────────────────────────────────────────┐
│              L2 (Wiki)                   │
│                                          │
│  온디맨드 접근 (~50-200 페이지)           │
│  ┌────────────────────────────────────┐  │
│  │ - 프로젝트 히스토리                 │  │
│  │ - 상세 워크플로우                   │  │
│  │ - 리서치 자료                      │  │
│  │ - 학습 노트                        │  │
│  │ - 분석/비교 문서                    │  │
│  └────────────────────────────────────┘  │
│  📖 /wiki query 명령으로 접근             │
└─────────────────────────────────────────┘
```

### 라우팅 원칙

**"이 정보를 몰랐을 때 어떤 실수가 발생하는가?"**

| 실수 유형 | 배치 | 예시 |
|-----------|------|------|
| 위험하거나 창피한 실수 | **L1** | API 키, 배포 규칙, 개인 선호 |
| 불편하지만 치명적이지 않은 실수 | **L2** | 프로젝트 히스토리, 기술 노트 |

### 크레덴셜 보안

- 위키는 보통 git으로 추적됨 → 크레덴셜이 들어가면 안 됨
- L1 (Claude Memory)은 git 추적에서 제외된 디렉토리에 위치
- 따라서 API 키, 비밀번호 등 민감 정보는 **반드시 L1에만 저장**

## 4. 듀얼 위키 앱 지원

### Logseq

```markdown
- 아웃라이너 포맷 (모든 줄이 독립적 블록)
- 인라인 프로퍼티: `property:: value`
- 자동 백링크 (그래프 네이티브)
- LLM이 append해도 기존 구조 파괴 없음
```

**장점**: 블록 수준 어드레싱으로 LLM 친화적. 추가만 하면 되므로 기존 콘텐츠와 충돌 없음

### Obsidian

```markdown
---
yaml: frontmatter
tags: [concept, tech]
---

# 플랫 마크다운 형식
일반적인 마크다운 작성 방식
```

**장점**: 수동 편집이 자연스러움. 풍부한 플러그인 생태계 (Dataview, Marp, Graph View)

### 비교 요약

| 항목 | Logseq | Obsidian |
|------|--------|----------|
| 데이터 포맷 | 아웃라이너 블록 | 플랫 마크다운 |
| 프로퍼티 | `property:: value` (인라인) | YAML frontmatter |
| LLM 쓰기 안전성 | ✅ 높음 (append-only) | ⚠️ 주의 필요 |
| 수동 편집 | 보통 | ✅ 자연스러움 |
| 플러그인 생태계 | 보통 | ✅ 풍부 |
| 그래프 뷰 | ✅ 네이티브 | ✅ 네이티브 |

## 5. 스키마 구조

### 8개 네임스페이스

위키 페이지를 다음 8개 영역으로 조직:

1. **Business** — 비즈니스 관련 지식
2. **Tech** — 기술/개발 지식
3. **Content** — 콘텐츠/미디어
4. **Projects** — 프로젝트별 정보
5. **People** — 인물/조직
6. **Learning** — 학습/교육
7. **Reference** — 참고 자료
8. **Careers** — 커리어/채용

### 5개 페이지 타입

| 타입 | 용도 | 필수 프로퍼티 |
|------|------|-------------|
| **Entity** | 사람, 도구, 조직 | 이름, 타입, 설명 |
| **Project** | 프로젝트 정보 | 상태, 시작일, 기술 스택 |
| **Knowledge** | 개념, 기술 노트 | 카테고리, 소스, 신뢰도 |
| **Feedback** | 피드백/회고 | 날짜, 컨텍스트, 액션 |
| **Hub** | 네임스페이스 진입점 | 하위 페이지 링크 |

## 6. 핵심 명령어

```bash
/wiki ingest <source>    # URL, 파일, 텍스트 처리 → 5-15 페이지 업데이트
/wiki query <question>   # 위키 검색 + 합성 답변 + 출처 표기
/wiki lint [--fix]       # 건강 검진: 고아 페이지, 오래된 콘텐츠, 깨진 참조, 크레덴셜 유출
/wiki status             # 위키 통계 대시보드
```

## 7. 5단계 Ingest 워크플로우

```
1. Analyze/Extract  →  소스 읽기 + 핵심 정보 추출
2. Wiki Scanning    →  기존 위키에서 관련 페이지 탐색
3. Page Updates     →  페이지 업데이트 (append-only, 덮어쓰기 금지)
4. Quality Gates    →  품질 검증 (메타데이터, 크로스레퍼런스)
5. Reporting        →  작업 결과 리포트 + 로그 기록
```

**중요 원칙**: append-only — 기존 콘텐츠를 절대 덮어쓰지 않고 추가만 함

## 8. 설정 파일 (llm-wiki.yml)

```yaml
tool: logseq              # 또는 obsidian
wiki_path: ~/wiki          # 위키 경로
memory_path: ~/.claude/    # L1 메모리 경로
lint:
  stale_threshold: 90      # 90일 이상 미업데이트 시 경고
  credential_patterns:     # 크레덴셜 탐지 패턴
    - "sk-"
    - "api_key"
    - "password"
language: ko               # 다국어 지원
```

## 9. 셋업 방법

```bash
git clone https://github.com/MehmetGoekce/llm-wiki.git
cd llm-wiki
./setup.sh
```

`setup.sh`가 수행하는 작업:
1. `/wiki` 스킬과 스키마 템플릿을 Claude Code에 복사
2. 위키 앱 타입 감지 (Logseq or Obsidian)
3. 초기 네임스페이스 구조 + 허브 페이지 생성

## 10. 관련 개념

- **CPU 캐시 계층 (L1/L2/L3)**: CPU가 자주 쓰는 데이터를 빠른 메모리에 배치하는 아키텍처. 이 프로젝트는 LLM 컨텍스트 윈도우를 "CPU"로, 지식을 "데이터"로 비유
- **컨텍스트 윈도우 최적화**: LLM이 한 번에 처리할 수 있는 토큰 수가 제한되므로, 무엇을 로드하고 무엇을 온디맨드로 가져올지가 핵심
- **Append-only 패턴**: 기존 데이터를 수정하지 않고 추가만 하는 방식. 데이터 무결성 보장 + 히스토리 보존
- **네임스페이스**: 위키 페이지를 도메인별로 구분하는 조직 체계
- **블록 기반 노트 (Logseq)**: 모든 줄이 독립적인 블록으로 취급되어, 프로그래밍 방식으로 조작하기 쉬운 구조

## 11. 이용 페르소나

### 페르소나 A: 솔로 개발자 / 프리랜서
- **프로필**: 여러 프로젝트를 병행하며, 각 프로젝트의 맥락을 빠르게 전환해야 하는 사람
- **고민**: Claude Code를 쓸 때마다 프로젝트 컨텍스트를 처음부터 설명해야 함
- **사용 흐름**: 프로젝트별 L2 페이지 구축 → Claude 세션 시작 시 L1 자동 로드 → `/wiki query`로 필요한 맥락만 가져옴
- **가치**: 컨텍스트 전환 비용 제로

### 페르소나 B: Logseq/Obsidian 기존 사용자
- **프로필**: 이미 Logseq이나 Obsidian으로 노트를 관리하고 있는 사람
- **고민**: 기존 노트를 활용하고 싶지만 새로운 도구를 배우기 싫음
- **사용 흐름**: 기존 위키에 `setup.sh` 실행 → 기존 노트가 L2가 됨 → Claude가 유지보수
- **가치**: 기존 워크플로우 유지하면서 AI 지식 관리 추가

### 페르소나 C: 보안에 민감한 사용자
- **프로필**: API 키, 크레덴셜 등 민감 정보가 많은 DevOps/인프라 엔지니어
- **고민**: 위키에 민감 정보가 섞여 들어가면 git push 시 유출 위험
- **사용 흐름**: 크레덴셜 → L1 (git 미추적), 일반 지식 → L2 (git 추적) 자동 분리
- **가치**: 지식 관리와 보안의 양립

## 12. 장단점

### 장점
- L1/L2 캐시 개념이 직관적이고 실용적
- Logseq/Obsidian 기존 사용자에게 친숙
- 크레덴셜 보안이 아키텍처 수준에서 해결
- MIT 라이선스, 경량 셋업 (`setup.sh` 한 번)
- 다국어 지원 (llm-wiki.yml의 language 설정)

### 단점
- Claude Code 전용 (다른 LLM 미지원)
- 웹 UI 없음 (터미널 + 위키 앱으로만 사용)
- 자동화가 약함 (수동 ingest/lint 필요)
